# 技术选型

说明句:确定 DrawDesk 的实现语言、界面框架与打包方式,并给出在当前开发机上可直接执行的结论.

---

## 一. 选型约束

本节列出影响语言选择的硬性条件.

---

- 平台:仅 Windows 10 与 Windows 11,无跨平台需求
- 核心能力:大量 Win32 调用,包括窗口枚举、DWM 隐藏、窗口布局、全局热键、托盘图标、进程启动
- 运行形态:常驻后台加悬浮工具条,要求空闲时低 CPU,低内存
- 使用环境:离线或内网,不依赖网络与云服务
- 分发要求:提供安装包,目标机可能没有开发环境
- 开发方式:单人长期维护,要求代码可测试,可读,可迭代
- 维护者熟悉度:用户熟悉 C++ 与 C,不熟悉 C#;长期可维护性优先于理论开发效率
- 本机现状:Node.js 26 与 npm 11 可用;.NET 8 运行时已装但没有 SDK;MSYS2 的 g++ 16.1 可用;没有 Rust 与 Visual Studio

## 二. 候选语言对比

本节从八个维度对候选语言评分,满分为五,熟悉度指维护者对该语言的掌握程度.

---

| 方案 | 开发效率 | Win32 能力 | 界面成本 | 体积 | 部署 | 可测试性 | 本机就绪 | 熟悉度 |
|---|---|---|---|---|---|---|---|---|
| C# 加 .NET 8 加 WinForms | 5 | 4 | 低 | 中 | 好 | 5 | 需装 SDK | 2 |
| C++17 加 Win32 | 3 | 5 | 中 | 极小 | 好 | 3 | 已就绪 | 5 |
| C 加 Win32 | 2 | 5 | 高 | 极小 | 好 | 2 | 已就绪 | 4 |
| Rust 加 windows-rs | 3 | 5 | 中 | 小 | 好 | 5 | 需装工具链 | 1 |
| Go 加第三方界面库 | 3 | 3 | 中 | 小 | 好 | 4 | 需装工具链 | 1 |
| Electron 或 Tauri | 4 | 2 | 低 | 极大 | 差 | 4 | 需装依赖 | 3 |
| Python 加 pywin32 | 4 | 4 | 中 | 大 | 差 | 4 | 需装依赖 | 2 |

### 2.1 C# 与 .NET 8

- 优势:WinForms 自带窗口、菜单与托盘组件;P/Invoke 调用 Win32 成熟稳定;System.Text.Json 内置;xUnit 可做单元测试;自包含发布后目标机零依赖
- 劣势:自包含体积偏大;NativeAOT 与 WinForms 不兼容,无法同时追求最小体积
- 结论:能力与开发效率最优,但维护者不熟悉,降为备选;仅在改为自行维护 C# 或交由他人维护时启用

### 2.2 C++17 与 Win32

- 优势:直接使用 Win32 与 DWM API,能力最完整;静态链接后为单个 exe,约 1 至 2 MB;本机工具链已就绪
- 劣势:界面需要自绘或引入第三方库;JSON 与测试框架需要自行准备;内存与句柄管理要求严格自律
- 结论:满足全部约束且维护者熟悉,定为首选

### 2.3 C 与 Win32

- 优势:体积最小,可低至几十 KB;无运行时依赖
- 劣势:字符串与容器全部手工处理;JSON 需引入 cJSON 等外部库;界面开发成本最高;内存错误风险最大;进度最慢
- 结论:维护者虽然熟悉,但相比 C++ 没有额外收益,不采用;仅在需要被其他程序嵌入等特殊场景考虑

### 2.4 其他方案

- Rust 的能力与体积都好,但本机没有工具链,学习与集成成本不占优,暂不采用
- Go 的界面生态薄弱,窗口能力依赖第三方库,不采用
- Electron 或 Tauri 体积大,常驻开销高,与低占用目标冲突,不采用
- Python 打包体积大,启动慢,常驻稳定性差,不采用

## 三. 结论

本节给出最终选择与切换条件.

---

- 首选方案 B:C++17 加 Win32,配套 MinGW-w64 静态编译与 Inno Setup 安装包
- 备选方案 A:C# 加 .NET 8 加 WinForms,仅在改为自行维护 C# 或交由他人维护时启用
- 决策依据:长期可维护性优先;维护者熟悉 C++ 与 C,不熟悉 C#
- 界面路线:Qt 6 加 QML,不使用自绘;已定案,详见第五节
- 两个方案共用同一套架构设计与数据模型,平台层是唯一差异,详见 `Design.md`

## 四. 打包与分发

本节确定发布方式与安装包方案,对应 `Roadmap.md` 的 M5 阶段.

---

| 发布方式 | 体积 | 目标机依赖 | 适用性 |
|---|---|---|---|
| 框架依赖 | 约 1 MB | 需 .NET 8 Desktop Runtime | 备选方案 A 使用;目标机不可控,不优先 |
| 自包含单文件 | 约 60 至 90 MB | 无 | 备选方案 A 的省心方式 |
| 自包含加裁剪 | 约 30 至 40 MB | 无 | 备选方案 A 体积敏感时尝试,需回归测试 |
| NativeAOT | 约 5 MB | 无 | 与 WinForms 冲突,不采用 |
| C++ 静态单文件 | 约 1 至 2 MB | 无 | 首选方案 B 的默认方式 |

- 若界面采用 Qt 等第三方库,体积以第五节结论为准;纯自绘不增加运行库依赖
- 安装包使用 Inno Setup 6,单个 exe 完成安装与卸载,离线可用,便于内网分发
- 第一版不做代码签名与自动更新,版本号写入安装包与关于页
- 配置与日志放在 `%APPDATA%\DrawDesk\DrawDesk\`,安装目录保持只读,避免权限问题

## 五. 界面技术路线

本节回答 C++ 能否实现现代化界面,并给出候选路线与验证计划.

---

- 结论:C++ 可以实现现代风格界面;本项目不采用自绘路线,选定 Qt 6 加 QML
- 现代观感的组成元素:无边框窗口,圆角,半透明或毛玻璃,柔和阴影,平滑动画,系统级字体与克制配色
- Windows 11 原生支持 Mica 与亚克力材质,窗口圆角与深色模式;Windows 10 使用纯色或轻量半透明降级,功能不受影响
- 决策依据:维护者不参与美术工作,自绘成本过高;Qt 提供现成控件与样式,声明式界面开发效率高;体积处于可接受范围

| 路线 | 效果上限 | 体积 | 开发成本 | 离线风险 | 说明 |
|---|---|---|---|---|---|
| Qt 6 加 QML | 很高 | 约 40 至 70 MB | 中 | 中 | 已选定;声明式界面,动画与圆角阴影实现简单;按 LGPL 动态链接分发 |
| 自绘,Win32 加 Direct2D 与 DirectComposition | 高 | 约 1 至 3 MB | 高 | 无 | 不采用;每一处控件都需要自己绘制,与维护者能力不匹配 |
| WebView2 加前端页面 | 最高 | 主程序小,运行时不固定 | 中 | 高 | 不采用;依赖系统 WebView2 Runtime,与离线原则冲突 |

- 界面子方案:使用 Qt Quick 与 QML,不使用 Qt Widgets;QML 的动画与视觉效果更现代,样式定制更方便
- 体积控制:当前 Debug 全量部署约 156 MB;M5 改 Release 构建, 并按 qmlimportscanner
  结果只复制所需 QML 模块, 目标部署目录 40 至 70 MB, 安装包 20 至 35 MB
- Qt 获取方式:Qt 官方在线安装器,组件选择与安装路径见 `Roadmap.md` 的 M0;备选方式为 MSYS2 软件包
- 验证计划:M1 阶段用 QML 实现工具条与抽屉切换动画原型,由用户确认风格后继续

## 六. Qt 许可与商用合规

本节说明 Qt 的许可模式与本项目的合规要点,供分发与商用参考.

---

- Qt 提供三种许可方式:LGPL v3,GPL v3,商业许可;同一套代码可以选择其中一种方式使用
- 本项目采用 LGPL v3 方式:可以闭源发布并商用,包括出售,不需要为 Qt 付费
- LGPL v3 方式的前提与义务:
  - 以动态链接方式使用 Qt,分发 Qt 的动态库文件,用户可自行替换
  - 随安装包附带 LGPL v3 与 GPL v3 许可文本,声明所使用的 Qt 版本
  - 提供 Qt 源码获取途径,通常是 Qt 官方下载地址
  - 不修改 Qt 源码;若修改,修改部分须按 LGPL 开源
  - 不分发时不产生义务,自己使用与公司内部部署不受限制
- 受影响的两条路径:静态链接 Qt,或使用 GPL 专用模块;这两种情况下整个软件必须以 GPL 开源,想闭源就只能购买商业许可
- 本项目所需模块均属 LGPL v3 范围;不使用 Qt Charts,Qt Data Visualization,Qt Virtual Keyboard 等 GPL 专用模块
- 需要购买商业许可的情形:希望静态链接以减小体积,公司合规不接受 LGPL,或需要修改 Qt 源码且不愿公开
- 以上为通行理解,正式商用发布前建议咨询法务或 Qt 官方;商业许可价格以官方报价为准

## 七. 对 C 是否最好的回答

本节直接回答语言选择问题.

---

- C 不是本项目的最佳选择. C 的优势在体积与无依赖,而本项目的难点不在性能或体积,而在 Win32 交互的正确性、界面交互与长期维护
- 用 C 需要手工处理字符串、动态数组、JSON 与界面,开发速度最慢,出错概率最高,维护成本最高
- 维护者熟悉 C,因此 C 是可行选项,但与 C++ 相比没有收益,故不采用
- 若最终目标是体积最小的单文件工具,首选方案的 C++17 已能达到同等量级,开发效率明显高于 C
- 关于 C#:开发效率更高,但维护者不熟悉,长期自维护成本反而更高,故不作为首选
